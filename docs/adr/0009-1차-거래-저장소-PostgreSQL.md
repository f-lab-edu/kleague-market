# ADR-0009: 1차 거래 저장소 = PostgreSQL

- 상태: 채택됨
- 날짜: 2026-08-24

## 맥락 (Context)

주문 한 건은 앞으로 주문 상태, 여러 체결, 양쪽 계정·보유량, 원장, 주문 이벤트를 함께 바꾼다.
이 변경은 일부만 성공하면 돈과 주식의 소유자가 맞지 않게 되므로 한 트랜잭션(전부 성공 또는 전부
롤백)이어야 한다. 호가창은 가격 우선·같은 가격이면 직렬 순서 우선으로 조회해야 하고, 중복 정산과
잘못된 참조는 DB 제약으로도 막아야 한다.

따라서 질문을 “MySQL과 PostgreSQL 중 무엇인가”로 바로 좁히지 않았다. 관계형, 문서형, 키-값, 그래프,
전용 이벤트 저장소, 전용 원장 DB, 분산 SQL, 임베디드 SQLite를 1차 저장소 후보로 비교했다. 비교
기준은 무엇을 저장하는지가 아니라 **무엇을 한꺼번에 안전하게 바꾸고 어떤 순서로 읽어야 하는가**였다.

### 현재 결정의 전제와 아직 모르는 것

- MVP는 단일 지역의 한 PostgreSQL 주 저장소에서 시작한다.
- 외부 API 호출은 거래 트랜잭션 밖에 두고, 핵심 쓰기는 한 DB 안에서 끝낸다.
- 운영 트래픽·응답 시간 목표·복구 시간의 실측값은 아직 없다.
- PostgreSQL이 모든 규모에서 최적이거나 MySQL보다 빠르다고 증명한 것이 아니다.
- 명시적 SQL과 행 잠금 동작을 직접 학습·검증하고, 전환 조건이 오면 다시 결정한다.

## 고려한 대안 (Considered Options)

- **PostgreSQL** — 다중 행 트랜잭션, 외래 키·유일·검사 제약, 명시적 행 잠금, 정렬 인덱스를 한
  저장소에서 제공한다. 활성 주문용 부분 인덱스처럼 의도를 직접 표현할 수 있다.
- **MySQL(InnoDB)** — 핵심 트랜잭션과 제약을 제공하므로 강한 대안이다. 다만 기본 격리 수준의
  gap lock(검색한 빈 인덱스 구간까지 잠그는 방식)과 활성 행 인덱스 표현을 별도로 설명해야 한다.
  실제 동일 workload 측정 없이 PostgreSQL보다 느리다고 판단하지 않는다.
- **문서형 DB** — MongoDB 등도 여러 문서 트랜잭션을 제공한다. 트랜잭션이 없어서 제외한 것이
  아니다. 이 프로젝트의 거래 경계가 한 주문 문서를 넘어 상대 주문·여러 사용자·보유·원장으로
  퍼지므로 문서 하나에 모으는 장점이 줄어든다.
- **키-값 DB** — DynamoDB 등도 여러 항목 트랜잭션을 제공한다. 확정된 키 조회와 대규모 자동
  확장에는 강하지만 거래별 접근 패턴, 보조 인덱스, 항목 수 경계, 관계와 여러 projection을
  애플리케이션이 더 많이 설계해야 한다.
- **그래프 DB** — 자전거래 탐지와 계정 관계 분석에는 좋지만 가격-시간 매칭과 정산의 1차 쓰기
  경로는 관계망 탐색 문제가 아니다.
- **전용 이벤트 저장소** — 감사·재생에는 강하다. 현재 규모에서는 관계형 DB의 append-only
  테이블로 주문 이벤트와 원장을 함께 저장하는 편이 운영 요소가 적다.
- **전용 원장 DB** — 이중 기록과 높은 처리량에는 강하지만 주문·호가·선수·사용자 관계 저장소를
  별도로 함께 운영해야 한다. 현재 원장은 PostgreSQL의 append-only 테이블로 시작한다.
- **분산 SQL** — 여러 지역에서 동시 쓰기와 지역 장애 생존이 필요할 때 유효하다. 같은 선수 주문은
  가격-시간 우선순위 때문에 어차피 직렬화되므로 DB 노드를 늘리는 것만으로 인기 선수의 처리가
  자동 병렬화되지는 않는다.
- **SQLite 같은 임베디드 DB** — 서버 없이 시작하는 단일 사용자 실험에는 가장 단순하다. 이
  프로젝트는 여러 요청·서버에서 공유하는 행 잠금과 동시 쓰기를 검증하려 하므로 1차 거래
  저장소에서는 제외한다.

검색 엔진, 시계열 DB, 분석용 열 지향 DB, 객체 저장소는 검색·분석·파일 보관의 보조 후보이지 이
거래 쓰기 경로를 책임질 1차 저장소 후보는 아니므로 상세 비교에서 제외했다.

## 결정 (Decision)

MVP의 1차 거래 저장소로 **PostgreSQL 17**을 채택한다. 애플리케이션은 명시적 SQL을 사용하는
Spring JDBC로 접근하고, 스키마는 Flyway migration으로 관리한다. 로컬 개발 DB와 실제 DB 통합
테스트는 Docker의 PostgreSQL 공식 이미지를 사용한다.

이 결정은 운영 최적성을 입증한 최종 결론이 아니라, 위 전제에서 가장 적은 구성 요소로 첫 거래
모델을 검증하기 위한 가역적인 제품 결정이다.

JPA는 현재 도입하지 않는다. 선수별 잠금, 가격-시간 조회, 여러 테이블 정산 쿼리를 직접 읽고
설명하는 것이 현재 학습·검증 목적에 더 맞는다.

## 근거 (Rationale)

- 주문·체결·계좌·보유·원장·이벤트의 변경을 한 로컬 트랜잭션으로 묶을 수 있다.
- 기본 키·외래 키·유일·검사 제약을 애플리케이션 검증의 최종 방어선으로 둘 수 있다.
- 가격과 직렬 순서를 조합한 인덱스 및 활성 주문 부분 인덱스를 SQL 스키마에 직접 표현할 수 있다.
- 여러 애플리케이션 인스턴스를 허용하면 `SELECT ... FOR UPDATE` 행 잠금을 직렬화 지점으로 삼아
  같은 잠금 규칙을 공유할 수 있다. 단일 인스턴스만 허용하면
  [[0005-매칭-동시성-모델|ADR-0005]]의 앱 메모리 락도 여전히 가능한 대안이며, 구체 잠금 방식은
  후속 PoC에서 좁힌다.
- 이벤트와 원장은 append-only 테이블로 두고, 현재 잔고·호가창은 같은 DB의 projection으로 시작할
  수 있어 전용 이벤트 저장소를 하나 더 운영하지 않아도 된다.
- PostgreSQL과 MySQL 모두 핵심 요구를 만족한다. PostgreSQL의 표현력과 잠금 동작이 현재 설계를
  설명하기 더 직접적이라는 이유로 첫 구현을 PostgreSQL에 고정한다. 성능 우위는 주장하지 않는다.

## 결과 (Consequences)

- **얻는 것**:
  - 거래 원자성, 관계와 제약, 정렬 조회를 한 제품에서 다루는 단순성
  - migration으로 재현되는 스키마와 실제 PostgreSQL 통합 테스트
  - 향후 여러 서버에서도 공유되는 DB 행 잠금 기반
- **감수하는 비용**:
  - 인기 선수 한 명의 쓰기는 선수별 직렬화 때문에 수평 확장만으로 빨라지지 않음
  - 스키마 변경과 인덱스·락·트랜잭션 운영 지식이 필요함
  - JDBC의 명시적 SQL과 행 매핑 코드를 직접 유지해야 함
  - Docker가 개발·통합 테스트의 필수 실행 조건이 됨
- **이 결정을 다시 볼 조건(번복 트리거)**:
  - 실제 부하 측정에서 단일 PostgreSQL의 처리 한계를 확인함
  - 여러 지역에서 동시에 쓰기를 받고 한 지역 장애 중에도 거래 접수를 계속해야 함
  - 확정된 접근 패턴과 작은 거래 항목 수를 바탕으로 DynamoDB형 설계가 총복잡도를 낮춤
  - 관계망 분석이 핵심 제품 기능이 되어 그래프 DB를 보조 저장소로 추가할 필요가 생김
  - SQL이 커져 컴파일 시점 타입 검사가 더 중요해지면 jOOQ 도입을 별도 검토함

Docker는 PostgreSQL 선택의 이유가 아니라 선택한 PostgreSQL을 같은 버전으로 실행·검증하는
수단이다. Docker Desktop을 운영 배포 방식으로 결정한 것은 아니다.
