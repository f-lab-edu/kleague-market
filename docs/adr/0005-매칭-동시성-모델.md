# ADR-0005: 매칭 동시성 실행 모델

- 상태: 채택됨
- 날짜: 2026-08-05

## 맥락 (Context)

P2P 호가창 매칭(ADR-0002)에서 **같은 선수 호가창에 동시 주문**이 몰리면 이중 체결·이중
차감(레이스 컨디션(race condition))이 생길 수 있다. 매칭을 어떤 동시성 모델로 실행할지 정해야 한다.

## 고려한 대안 (Considered Options)

- **글로벌 락** — 전체 매칭을 하나로 직렬화. 단순하지만 선수 무관하게 한 번에 하나라 **처리량 붕괴**.
- **선수별 직렬화 + 동기 DB 트랜잭션** — 선수 단위로만 직렬화, 다른 선수는 병렬. ← 선택
- **큐 기반 비동기 인메모리 단일 라이터**(선수별 큐/액터) — 빠르지만 메모리↔DB 일관성·크래시 복구가 복잡.

## 결정 (Decision)

**선수별 직렬화 + 요청 스레드 동기 DB 트랜잭션 매칭.**
- 주문 생성 → 매칭 → 체결(fill) → 잔고·보유 정산 → 잔량 호가 등록 = **단일 트랜잭션**(실패 시 전부 롤백).
- 같은 선수 주문은 **선수별 락**(예: `SELECT … FOR UPDATE` 또는 앱 레벨 per-player 락)으로 한 번에 하나. 다른 선수는 병렬.

## 근거 (Rationale)

- **정확성 우선**: DB 트랜잭션이 원자성·durability를 공짜로 주어 인메모리 엔진의 복구·일관성 리스크를 피한다.
- **선수별 직렬화로 병렬성 확보** — 글로벌 락의 처리량 붕괴를 피함. 선수는 서로 독립.
- **락 점유 최소화**: 임계 구역엔 호가창 조회·매칭·정산 저장만. **외부 API 호출·긴 연산은 락 밖**(성능·데드락(deadlock) 방지).
- **취소 vs 체결 동시** → 직렬화라 락 획득 순서가 승자, **둘 다 성공 없음**(이중 지불 방지).

## 결과 (Consequences)

- **얻는 것**: 정확성(원자성·무결성), 선수별 병렬 처리량, 단순한 추론·테스트, 동시성 테스트로 증명 가능.
- **감수하는 비용**: 처리량이 DB·선수별 락에 묶임(초고빈도엔 부적합, 게임엔 충분).
- **재검토/번복 조건**: 특정 선수 호가창이 병목(초당 수천 주문)이 되면 **큐 기반 비동기 단일 라이터(인메모리)**로 진화(새 ADR). 그 진화의 기반이 불변 이벤트 로그([[0006-이벤트-로그-데이터-캡처|ADR-0006]]).
