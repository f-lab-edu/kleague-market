# ADR-0008: 빌드 규약 공통화 = build-logic 컨벤션 플러그인

- 상태: 채택됨
- 날짜: 2026-08-07

## 맥락 (Context)

멀티모듈 3개(ADR-0001)의 `build.gradle`이 같은 설정을 반복하고 있었다.
`plugins { id 'java' }`와 `java { toolchain { languageVersion = 21 } }`가 세 곳에 그대로 복제돼,
Java 버전을 올리려면 세 파일을 다 고쳐야 하고 한 곳을 빠뜨리면 모듈마다 컴파일 타깃이 갈린다.

앞으로 테스트 설정(JUnit 플랫폼), 컴파일러 옵션, 정적 분석이 들어오면 이 중복은 더 커진다.

동시에 toolchain 설정이 **로컬에 JDK 21이 설치된 머신에서만** 동작하는 상태였다.
설치돼 있으면 Gradle이 자동 탐지해 통과하므로 문제가 드러나지 않지만,
없으면 다음으로 실패한다(실측 확인):

```
Cannot find a Java installation on your machine matching: {languageVersion=21, ...}.
Toolchain download repositories have not been configured.
```

CI 워크플로(`.github/workflows/sonarcloud-analyze.yml`)는 JDK 19를 설치하므로
빌드·테스트를 CI에서 돌리는 순간 같은 실패를 만난다.

## 고려한 대안 (Considered Options)

**규약 공통화**

- **A. 각 모듈에 그대로 중복** — 지금 상태. 파일 수는 가장 적다.
- **B. 루트 `build.gradle`의 `allprojects`/`subprojects`** — 한 곳에서 하위 모듈에 설정을 주입.
- **C. `build-logic` 컨벤션 플러그인**(미리 컴파일된 스크립트 플러그인) ← 선택

**toolchain 가용성**

- **D. 그대로 둠** — 개발자가 JDK 21을 직접 설치.
- **E. foojay 리졸버로 자동 프로비저닝** ← 선택

## 결정 (Decision)

공통 규약을 `build-logic`의 컨벤션 플러그인 `kleague.java-conventions`로 추출하고,
`settings.gradle`에 foojay 리졸버를 추가해 JDK 21을 자동 프로비저닝한다.

## 근거 (Rationale)

**B(`allprojects`/`subprojects`)를 고른 게 아닌 이유**

- **모듈이 자기 빌드를 설명하지 못한다.** `domain/build.gradle`만 읽어서는 어떤 Java 버전으로
  컴파일되는지 알 수 없고, 루트 파일을 함께 봐야 한다. 설정이 **주입**되기 때문이다.
- **선언이 아니라 명령이다.** 컨벤션 플러그인은 모듈이 `id 'kleague.java-conventions'`로
  **필요한 규약을 선언**한다. `subprojects`는 루트가 하위에 **강제**한다.
  모듈마다 다른 규약이 필요해지는 순간(예: 순수 자바 모듈 vs Spring 모듈)
  `subprojects { if (name == ...) }` 같은 분기가 자라기 시작한다.
- **구성 캐시·병렬 빌드와 궁합이 나쁘다.** 루트 프로젝트가 하위 프로젝트 객체를 직접 건드리는
  교차 프로젝트 설정(cross-project configuration)이라, Gradle이 프로젝트 간 격리를 보장하지 못한다.
- Gradle 공식 문서도 `subprojects`/`allprojects`를 권장하지 않는다.

**A(중복 유지)를 고른 게 아닌 이유**

지금 중복은 6줄 남짓이라 그 자체로는 견딜 만하다. 실제로 `build-logic` 도입은
**당장 지우는 줄보다 새로 만드는 파일이 많다**(파일 3개 추가 : 중복 6줄 제거).
그럼에도 고른 것은 이 규약이 **자라는 방향이 확정돼 있어서**다 —
다음 사이클에 테스트 설정이, 그다음에 정적 분석이 들어온다.
그때마다 세 파일을 고치는 비용이 지금 한 번 만드는 비용을 넘는다.

**E(foojay 자동 프로비저닝)를 고른 이유**

- 자동 탐지만으로는 **"내 머신에서는 되는데"** 상태가 된다. 실제로 그랬다.
- 리뷰어·CI가 JDK 21을 미리 깔아야 한다는 암묵적 전제를 없앤다. 빌드가 스스로 조달한다.
- 비용은 최초 1회 다운로드(약 1분 30초)뿐이고 이후 캐시된다.

## 결과 (Consequences)

- **얻는 것**
  - Java 버전·공통 규약을 **한 곳**(`build-logic/src/main/groovy/kleague.java-conventions.gradle`)에서 바꾼다
  - 모듈 `build.gradle`에는 **그 모듈 고유의 것만** 남는다(의존성, Spring 플러그인)
  - JDK 21이 없는 머신·CI에서도 빌드된다. 검증: 자동 탐지를 끈 상태에서
    Temurin 21.0.12를 내려받아 `BUILD SUCCESSFUL`, 바이트코드 major 65(=Java 21) 확인
  - `domain`의 순수성은 유지된다 — 컨벤션 플러그인은 `java`·toolchain·repositories만 넣고
    Spring을 넣지 않는다. `:domain:dependencies --configuration compileClasspath`가 `No dependencies`(ADR-0001)

- **감수하는 비용**
  - 파일 3개(`build-logic/`)와 개념 하나(포함된 빌드, included build)가 늘어난다
  - 규약을 바꾸려면 `build-logic`을 재컴파일하므로 빌드가 아주 조금 느려진다
  - 최초 빌드에서 JDK를 내려받는 시간(약 1분 30초)이 든다

- **이 결정을 다시 볼 조건(번복 트리거)**
  - 모듈이 계속 3개에 머물고 공통 규약이 **끝내 자라지 않으면** — 그때는 `build-logic`이
    순수 오버헤드이므로 각 모듈에 되돌리는 편이 낫다
  - 규약이 여러 갈래로 갈라지면(예: 순수 자바용 / Spring용 / 테스트 픽스처용)
    컨벤션 플러그인을 **여러 개로 분리**한다. 하나에 `if` 분기를 넣지 않는다
  - 사내·조직 표준 빌드 플러그인을 별도 저장소에서 배포하게 되면 `build-logic`을 그쪽으로 옮긴다
