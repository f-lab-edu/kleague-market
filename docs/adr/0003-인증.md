# ADR-0003: 인증 = 헤더 Bearer 서버측(opaque) 토큰

- 상태: 채택됨
- 날짜: 2026-08-02

## 맥락 (Context)

MVP 인증 방식을 정해야 한다. 클라이언트에 **모바일이 포함**(비전상 필수)된다.
초기 API 명세의 인증이 얇다는 지적이 있었다.

## 고려한 대안 (Considered Options)

- **세션-쿠키** — Spring Security 기본, 서버 세션 + 쿠키.
- **무상태 JWT** — 자체 서명 토큰, 서버 저장 없이 검증.
- **헤더 Bearer + 서버측(opaque) 토큰** — 헤더로 오는 토큰이지만 서버가 보관·무효화. ← 선택

## 결정 (Decision)

**헤더 `Authorization: Bearer <token>` + 서버측 opaque 토큰.**
로그인 시 서버가 랜덤 토큰을 발급·저장하고, 요청마다 헤더 토큰을 조회해 검증한다.
무상태 JWT는 멀티서비스/수평확장이 필요해질 때 전환한다.

## 근거 (Rationale)

### 1) 두 축을 분리해서 판단 (핵심)

흔히 뭉개는 두 축을 나누면 답이 정확해진다:

| 축 | 무엇이 결정 | 우리 선택 |
|----|------------|----------|
| 쿠키 vs **헤더** | 클라이언트 종류 | 모바일 있음 → **헤더 Bearer** |
| **서버측** vs 무상태(JWT) | 규모·멀티서비스 | 아직 단일 노드 → **서버측** |

**모바일은 첫 축만 뒤집는다(→헤더).** JWT(무상태)를 요구하는 게 아니다.

### 2) 서버측 토큰이 지금 더 낫다

- **즉시 무효화**: 로그아웃·토큰 탈취 시 서버에서 지우면 끝. JWT는 무상태라 무효화가 어렵고
  리프레시 회전·블랙리스트 같은 비용을 떠안는다 — 지금 그 이점(무상태)이 필요 없다.
- 구현 후보: Spring Session 헤더 세션 리졸버, 또는 단순 토큰 스토어.

### 3) "가볍다"는 방식이 아니라 엄밀함으로 해소

인증을 "충분"하게 만드는 건 토큰 종류가 아니라 다음이다:

- **BCrypt 비밀번호 해시**(평문 금지)
- **보호 범위**: 주문·포트폴리오·내역 = 인증 / 시세·마켓 = 공개
- **토큰 생명주기**: 만료 + 로그아웃 무효화
- (쿠키였다면) **CSRF** — 헤더 Bearer는 이를 피하지만 XSS 토큰 탈취를 대신 안게 됨

### 4) 메커니즘 격리로 전환 비용 최소화

컨트롤러·서비스는 세션/토큰을 모르고 **`CurrentUser`/`SecurityContext`에만 의존**한다.
→ 나중에 JWT로 바꿔도 시큐리티 설정만 교체, 도메인·유스케이스는 무수정.

## 결과 (Consequences)

- **얻는 것**: 단순함, 즉시 무효화, 모바일 호환, 저비용 전환 여지.
- **감수하는 비용**: 서버측 토큰 저장소 유지.
- **재검토/번복 조건**: 멀티서비스·수평확장·제3자 클라이언트가 현실이 되면 JWT로 전환
  (별도 ADR + 세션/서버측/JWT 비교 기록).
