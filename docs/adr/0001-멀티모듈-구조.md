# ADR-0001: 멀티모듈 구조 (app / domain / kleague-client)

- 상태: 채택됨
- 날짜: 2026-08-01

## 맥락 (Context)

기능이 확정되지 않은 초기 단계에서 Gradle 프로젝트 구조를 먼저 설계해야 했다.
앱은 Spring Boot, 외부 API(api-sports) 연동, 거래 도메인이 예정돼 있다.
기능 단위로 나눌 근거가 아직 없어 **모듈의 성격(레이어)** 기준으로 나눌지를 결정해야 했다.

## 고려한 대안 (Considered Options)

- **단일 모듈** — 전부 `app` 하나에.
- **패키지 분리** — 한 모듈 안에서 `domain` / `client` 패키지로만 구분.
- **멀티모듈** — `app` / `domain` / `kleague-client` 세 모듈. ← 선택

## 결정 (Decision)

성격(레이어) 기반 **3모듈**로 분리한다.

| 모듈 | 책임 | Spring 의존 |
|------|------|:---:|
| `app` | 실행(Spring Boot main), 유스케이스 조율·조립, 인프라 어댑터, 트랜잭션 경계 | O |
| `domain` | 순수 자바 비즈니스 규칙 + 포트(인터페이스) | **X** |
| `kleague-client` | 외부 API(api-sports) → 도메인 타입 번역(Anti-Corruption Layer) | 격리 |

## 근거 (Rationale)

### 1) 모듈 경계 = 의존성 방향의 컴파일 타임 강제

패키지는 "지켜야 함(shouldn't)"이라 규율에 의존한다. 모듈은 `domain`의 build.gradle에
Spring이 없어 아래가 **컴파일 자체가 안 된다(can't)**:

```java
// domain 안에서
import org.springframework.stereotype.Service; // ← 클래스패스에 없어 컴파일 실패
```

순수성을 "지키자"가 아니라 "불가능"으로 만든다.

### 2) 순수 domain이 주는 구체 이득

- **컨테이너 없는 빠른 테스트**: `new PriceRule(fakeRepo).apply(...)` → 밀리초. `@Autowired` 필드가 박히면 `new`로 인스턴스화조차 안 돼 `@SpringBootTest`(초 단위)가 강제된다. 규칙 테스트가 수백 개면 이 차이가 폭발한다.
- **Spring 버전 churn에서 격리**: Boot 2→3, `javax`→`jakarta` 전환은 `app`만 건드리고 규칙은 그대로.
- **가독·추론**: 프록시·빈 생명주기 없이 규칙만 읽힌다.

### 3) kleague-client = Anti-Corruption Layer

외부 API 응답 형식은 통제 불가 — 필드명이 예고 없이 바뀌거나 제공처가 통째로 교체될 수 있다.
번역을 이 모듈에 가둬 **수정 범위를 한 곳으로** 만든다. 식별자도 내부 id로 발행하고
api-sports id는 매핑 컬럼으로만 둔다([[2026-07-29-kleague-market-design]] D6).

### 4) "repository는 Spring인데?" 모순은 포트-어댑터로 해소

인터페이스는 **소비자(domain)**가 소유한다(의존성 역전, SOLID의 D):

```java
// domain (순수 자바)
interface PlayerRepository { Player findById(PlayerId id); }   // 포트
class PriceRule { int apply(Player p, ...) { ... } }           // 규칙(POJO)

// app (Spring)
@Repository
class JpaPlayerRepository implements PlayerRepository { ... }  // 어댑터(Spring Data)

@Service
class TradeService {                         // 응용 서비스 = 조율 + 트랜잭션 경계
    private final PlayerRepository repo;      // 타입은 domain 인터페이스
    @Transactional                            // 트랜잭션은 app
    void execute(...) { var p = repo.findById(...); priceRule.apply(p, ...); }
}
```

의존은 **`app → domain` 한 방향**뿐이고 domain은 바깥을 가리키지 않는다.
연결은 빌드 플러그인이 아니라 **런타임 Spring DI**, 그 조립을 **app이 담당**한다.
**규칙 = domain, 조율 = app.**

## 결과 (Consequences)

- **얻는 것**: 강제된 순수성, 컨테이너 없는 빠른 규칙 테스트, 인프라·데이터 제공자 교체의 국소화, 명확한 책임 분리, 학습/포트폴리오 가치.
- **감수하는 비용**: 모듈별 `build.gradle` 등 설정 증가 → **컨벤션 플러그인(build-logic)으로 공통화**(`allprojects`/`subprojects`는 지양). 포트-어댑터의 간접성.
- **경계 함정**: 규칙이 app 응용 서비스로 새는 **fat service / anemic domain** 안티패턴 회피 — 규칙은 domain 객체 안에, app 서비스는 얇게.
- **재검토/번복 조건**: 프로젝트가 사소한 CRUD로 축소되거나 모듈 경계가 개발을 방해하면 재고. `domain` 내부는 필요 시 더 분할 가능.
