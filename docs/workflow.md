# workflow

`kleague-market`의 작업 방식. 목표는 완성을 넘어 **설계와 코드를 완전히 이해하고 넘어가는 것**.
기억 시스템의 경계는 [[README]] 참고.

## 대원칙

- **이해가 속도보다 우선.** 이해 안 된 채로 다음 기능으로 넘어가지 않는다.
- **읽기는 위임하고, 쓰기는 위임하지 않는다.** 서브에이전트는 과정을 숨겨서 학습을 해친다.
  검증·리뷰(읽기)는 결과물이 곧 학습 재료라 위임해도 되지만, 구현·테스트 작성은 그 과정이 배울 것 자체다.
  → [[#서브에이전트 사용 규칙]]
- **문서는 한 곳에만.** 같은 내용을 Notion·docs 양쪽에 독립 작성하지 않는다. Notion은 docs에서 파생.

## skill 사용 지도 (언제 → 무엇)

| 상황/신호 | skill | 하는 일 |
|-----------|-------|---------|
| "X를 만들자", 목표가 흐릿함 | `brainstorming` | 코드 전, 의도·요구사항·설계 확정 |
| 요구사항 잡힘, 다단계 작업 | `writing-plans` | 단계별 계획 문서화 (성공 기준 명시) |
| 기능/버그 구현 직전 | `test-driven-development` | 테스트 먼저 → 최소 코드로 통과 |
| 코드 짤 때 항상 | `ponytail` + `karpathy-guidelines` | 최소 코드 / 수술적 변경·가정 명시 |
| 버그·테스트 실패·이상 동작 | `systematic-debugging` | 추측 금지, 근본 원인부터 |
| "다 됐다" 직전 | `verification-before-completion` + `/verify` | 실제 실행해 증거 확인 |
| 기능 완료·머지 전 | `requesting-code-review` / `/code-review` | 요구사항·품질 점검 |
| 리뷰 피드백 받음 | `receiving-code-review` | 맹목 수용 말고 검증 후 반영 |
| 브랜치 마무리 | `finishing-a-development-branch` | 통합 방식 결정 |
| 격리 필요 (나중) | `using-git-worktrees` | 작업 공간 분리 |
| 문서 고친 뒤·구현 착수 전 | `docs-auditor` (에이전트) | 스펙·ADR·API 계약 교차 정합성 검사 |
| 구현 끝, 커밋·PR 전 | `code-reviewer` (에이전트) | 코드가 D0~D9·ADR을 지키는지 검사 |

## 한 기능 사이클

1. **brainstorming** — 무엇을/왜. 목표가 흐릿하면 무조건 여기부터.
2. **writing-plans** — 요구사항이 잡히면 단계별 계획. 성공 기준(검증 방법)을 각 단계에 적는다.
3. **이해 확인** — 코드 전, 내가 설계를 설명하고 당신이 되짚는다(teach-back). 막히면 2번으로.
4. **구현** — `test-driven-development` + `ponytail`(최소 코드) + `karpathy`(가정 명시).
5. **검증** — `verification-before-completion` + `/verify`. 실제로 돌려 증거 확인. 추측 금지.
6. **리뷰** — `/code-review`. 피드백은 `receiving-code-review`로 검증 후 반영.
7. **docs 갱신 (DoD)** — 이 사이클에서 바뀐 아키텍처/결정을 `[[architecture]]`·`adr/`에 반영.
   **이걸 해야 기능 완료.** 안 하면 위키가 썩는다.
8. **마무리** — 커밋/브랜치. `finishing-a-development-branch`로 통합 결정.
   (Claude-Mem이 세션 로그를 자동 기록한다.)

## 세션 나누기

**한 기능 사이클을 한 세션에 다 넣지 않는다.** 컨텍스트가 차면 판단이 흐려지고, 중간에 끊기면 맥락을 잃는다.
사이클 단계 경계에서 끊는다 — 컨텍스트 퍼센트를 보고 끊는 게 아니라, 일이 한 매듭 지어졌을 때 끊는다.

| 세션 | 사이클 단계 | 하는 일 | 끝내는 신호 |
|------|------------|---------|------------|
| ① 설계·계획 | 1~3 | `brainstorming` → `writing-plans` → 이해 확인(teach-back). `docs-auditor`로 스펙 정합 확인 | 계획 문서 커밋 |
| ② 구현 | 4~5 | `test-driven-development`로 계획 실행. **직접 짠다, 위임 안 한다** | 테스트 통과 + 커밋 |
| ③ 리뷰·문서 | 6~8 | `code-reviewer` 호출 → 피드백 검증 후 반영 → docs 갱신(DoD) | PR·머지 |

- **세션을 끊기 전 반드시 커밋한다.** Claude-Mem이 로그를 남기지만, 진실의 출처는 git과 이 `docs/`다.
- 다음 세션은 Claude-Mem + `docs/`로 맥락을 복원한다. **별도 핸드오프 문서를 쓰지 않는다** (문서는 한 곳에만).
- 한 단계가 커서 세션이 또 차면, 그 단계를 더 잘게 쪼갠다. 계획이 너무 컸다는 신호다.

## 서브에이전트 사용 규칙

에이전트 정의는 `.claude/agents/`에 있고 git으로 관리한다.

| | 위임 | 이유 |
|---|:---:|---|
| `docs-auditor` — 문서 교차 정합성 | ✅ | 문서 10개 대조는 읽기. 결과(모순 목록)가 곧 학습 재료다 |
| `code-reviewer` — 코드의 스펙 준수 | ✅ | 스펙 대비 검증은 읽기. 고치는 건 내가 한다 |
| 구현 · 테스트 작성 | ❌ | 그 과정이 배울 것 자체다 |
| 설계 판단 · ADR 작성 | ❌ | 콜드 스타트라 확정된 맥락(D0~D9)을 모른 채 엉뚱하게 간다 |

- **쓰기 도구를 주지 않는다.** `docs-auditor`는 `Read`/`Grep`/`Glob`뿐이고, `code-reviewer`만 빌드·테스트 실행을 위해 `Bash`를 갖는다
  (파일 쓰기는 프롬프트로 금지 — 도구 제약과 지시의 이중 방어). 보고서만 반환하고, 고치는 건 메인 세션에서 사람이 판단해 한다.
- 병렬로 여러 작업을 동시에 굴리지 않는다. 동시에 3개가 돌면 3개 다 이해 못 한 채 넘어간다.
- 에이전트 보고서도 `receiving-code-review`처럼 다룬다 — 맹목 수용 말고 근거 인용을 직접 확인한 뒤 반영한다.

## 버그가 나면

사이클 어디서든 버그·이상 동작이 보이면 즉시 `systematic-debugging`.
증상만 패치하지 말고, 같은 함수의 모든 호출부를 확인해 근본 원인을 한 번에 고친다.
