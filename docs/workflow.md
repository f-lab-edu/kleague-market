# workflow

`kleague-market`의 작업 방식. 목표는 완성을 넘어 **설계와 코드를 완전히 이해하고 넘어가는 것**.
기억 시스템의 경계는 [[README]] 참고.

## 대원칙

- **이해가 merge의 조건이다.** 이해 못 한 코드는 merge하지 않는다.
  구현이 빨라진 만큼 미리뷰 재고가 쌓이므로, **미리뷰 Draft PR이 0개여야 다음 구현을 연다**(같은 Issue를 이어서 하는 건 예외).
- **초안은 위임하고, 최종 판단은 위임하지 않는다.**
  구현·테스트와 **가역적이고 Issue 범위 안의 설계 초안**은 `/issue-implement`가 결정하고 근거를 남긴다.
  사람은 Draft PR에서 그 결정을 **최종 수용·수정·기각**한다.
  ADR급·고위험 결정은 **구현 전에** 사람이 확정한다.
  이해는 코드 작성 전 teach-back이 아니라 **PR 리뷰에서** 확보한다. → [[#서브에이전트 사용 규칙]]
- **문서는 한 곳에만.** 같은 내용을 Notion·docs 양쪽에 독립 작성하지 않는다. Notion은 docs에서 파생.

## 한 기능 사이클

1. **Issue 작성** — 범위 계약. 목표·범위·**비목표**·완료 조건. 자연어로 던지면 `/issue-implement`가 대신 만든다.
2. **`/issue-implement` 호출** — 스킬이 **Design Freeze를 Issue 댓글로 기록**한 뒤(사람이 따로 쓰지 않는다) 테스트·구현·검증·자체 리뷰·Draft PR까지 간다. 형식적 승인 요청 없이 진행한다.
3. **Draft PR 도착** — 여기서 세션을 끊는다.
4. **리뷰·학습** — **새 세션에서** PR diff를 읽는다. `/learn` 또는 teach-back. **여기가 학습 지점이다.**
5. **수정** — 이해 안 된 곳, 동의 안 되는 곳을 고친다(직접 또는 지시).
6. **docs 갱신·최종 검증 → merge (DoD)** — 바뀐 아키텍처/결정을 **같은 PR 안의** `adr/`·스펙·`openapi.yaml`에 반영한다. 문서와 코드가 함께 검증된 뒤 사람이 merge한다. **이걸 해야 기능 완료.**

기존 3번(코드 작성 전 teach-back)은 없어진 게 아니라 **4번으로 옮겨졌다.** 아직 없는 코드를 설계 수준에서 먼저 완전히 이해하려 하면 학습이 구현의 선행 조건이 되어 구현이 계속 밀린다. 실제로 도는 코드를 놓고 배우는 쪽이 낫다.

## 세션 나누기

**구현과 리뷰를 같은 세션에 넣지 않는다.** 구현한 세션이 리뷰까지 하면 사람이 구현자의 프레이밍을 그대로 따라가고, 콜드 스타트로 읽을 때만 보이는 구멍이 안 보인다. (`code-explainer`를 만든 이유와 같다.)

| 세션 | 사이클 단계 | 하는 일 | 끝내는 신호 |
|------|------------|---------|------------|
| ① 구현 | 1~3 | Issue 확인·생성 → `/issue-implement`(Design Freeze 포함) | Draft PR 생성 |
| ② 학습·리뷰 | 4~6 | **새 컨텍스트에서** `/learn` → 코드 흐름 설명 → 수정 → Ready 전환 | merge |

- **세션을 끊기 전 반드시 커밋한다.** 진실의 출처는 git과 이 `docs/`다.
- 다음 세션은 Claude-Mem + `docs/` + Issue로 맥락을 복원한다. **별도 핸드오프 문서를 쓰지 않는다.**
- PR이 커서 한 세션에 리뷰가 안 끝나면, 그건 Issue를 더 잘게 쪼갰어야 한다는 신호다.

## 서브에이전트 사용 규칙

에이전트 정의는 `.claude/agents/`에 있고 git으로 관리한다.
단 `code-explainer`와 `/learn`은 **사용자 레벨**(`~/.claude/`)이라 이 저장소에 없다 — 개인 학습 장치다.

| | 위임 | 이유 |
|---|:---:|---|
| `docs-auditor` — 문서 교차 정합성 | ✅ | 문서 10개 대조는 읽기. 결과(모순 목록)가 곧 학습 재료다 |
| `code-reviewer` — 코드의 스펙 준수 | ✅ | 스펙 대비 검증은 읽기 |
| 구현 · 테스트 작성 | ⚠️ | **`/issue-implement`가 한다.** 이건 서브에이전트가 아니라 **메인 세션 스킬**이라 아래 "쓰기 도구 금지"에 걸리지 않는다. 학습은 PR 리뷰에서 |
| 가역적이고 Issue 범위 안의 설계 판단 | ✅ | 결정하고 Design Freeze·PR에 근거를 남긴다 |
| **ADR 확정** · 고위험 결정 | ❌ | 초안 작성은 되지만 **확정은 사람이 한다.** 고위험 = 공개 API 파괴·스키마·인증·모듈 경계·동시성 모델·새 의존성 |

- **에이전트에 쓰기 도구를 주지 않는다.** `docs-auditor`는 `Read`/`Grep`/`Glob`뿐이고, `code-reviewer`만 빌드·테스트 실행을 위해 `Bash`를 갖는다
  (파일 쓰기는 프롬프트로 금지 — 도구 제약과 지시의 이중 방어). 보고서만 반환한다.
  명백한 스펙 위반은 `/issue-implement`가 고치고, **판단이 갈리는 건 PR의 `### 구현자가 확인받고 싶은 판단`에 적는다.**
- 병렬로 여러 작업을 동시에 굴리지 않는다. 동시에 3개가 돌면 3개 다 이해 못 한 채 넘어간다.
- 에이전트 보고서도 `receiving-code-review`처럼 다룬다 — 맹목 수용 말고 근거 인용을 직접 확인한 뒤 반영한다.

## 버그가 나면

사이클 어디서든 버그·이상 동작이 보이면 즉시 `systematic-debugging`.
증상만 패치하지 말고, 같은 함수의 모든 호출부를 확인해 근본 원인을 한 번에 고친다.
