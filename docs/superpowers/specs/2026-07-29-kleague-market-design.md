# kleague-market 설계 스펙

> 상태: **기획 확정(MVP).** 튜닝 상수(공급 N·시작 포인트·수수료율·배당 가중치 등)는 구현 시 캘리브레이션.
> 아키텍처 대안 결정은 별도 `adr/`(0001 멀티모듈 · 0002 거래모델 · 0003 인증 · 0004 데이터소스 · 0005 매칭동시성 · 0006 이벤트로그 · 0007 상장폐지 · 0008 빌드규약)로 분리 기록. 여기엔 제품·경제·게임 규칙. [[README]]·[[workflow]] 참조.

## 비전 (한 줄)

K리그 선수를 자산으로 사고파는 **가상 포인트 기반 판타지 주식 거래소**. 실제 경기 성적이 배당으로 반영됨.

## 데이터 현실 (api-sports v3, K리그 = league **292** = K League 1)

실제 응답 probe + 교차리그 검증으로 확정(설계는 이 현실에 맞춤):
- ✅ **옴**: `fixtures`(일정·스코어·상태), `fixtures/events`(골·어시·카드·교체), `fixtures/lineups`(선발), `standings`, `teams`, `leagues`, `players/topscorers`·`topassists`(rating 포함, **상위 선수만**), `players/squads`(로스터).
- ⚠️ **sparse**: `players?league&season`(시즌 집계) — 2023은 **일부만** 채워지고 다수 null, `tackles`/`saves` 거의 null.
- ⚠️ **부분(~35%)**: `fixtures/players`(경기별 rating·minutes)는 **경기마다 있기도/없기도**. 2024 FT 20경기 샘플 중 **7경기만** 데이터(results:2), 나머지 results:0. 있을 때는 **팀당 20명·rating·minutes·saves 정상**(예: rating 6.3, 90분). 커버리지 플래그 `statistics_players=true`지만 실제 불완전. (유료 결제가 historical 공백을 메울지 불확실 → 필요 시 라이브 2026으로 재확인. tackles는 채워진 경기에서도 종종 null.)
- **함의**: per-match rating·minutes가 **~65% 경기에 없어 배당을 그에 의존 불가** → **배당 = events + 팀 결과**(events/lineups/score는 전 경기 가용). **출전자 = 라인업+교체이벤트로 파생**(minutes 없어도 됨). 시즌 개인스탯 sparse → **base value = 계층형 floor**.
- 무료 플랜: 10req/분, 100req/일. ~2024 무료, 2026 유료.
- **대안(2차)**: 공공데이터포털(data.go.kr)엔 K리그 경기/선수 기록 없음(등록정보류만). 공식 상세는 **허가받은** K리그 공식 데이터 포털(무단 크롤링은 ToS 위반 — 도메인·약관 판단은 ADR-0004에 기록) 또는 타 제공자 — per-match 성적이 핵심이 되면 이 경로. MVP는 api-sports만.

## 확정된 결정

### D0. 거래 모델 → **P2P 호가창 + 매칭 엔진** (→ ADR-0002)
- 사용자 간 지정가 주문을 매칭. 가격은 체결로 **형성**(가격 발견, price discovery).
- "시스템-상대(AMM)"는 채택 안 함 → 2차 **마켓메이커 봇**이 호가창의 한 참가자로 흡수(유동성·파산방지·성적→시세를 봇 하나로 해결).
- 원칙: **거래가 가격을 만들고, 성적은 배당을 만든다**(두 시스템 분리).

### D1. 주식 발행/공급 + base value
- 선수당 **고정 총발행량**, 전 선수 **균일 N주**(구체 N 미정).
- 상장 시 **시스템이 전량 시드**(base value에 매도호가) → 이후 순수 P2P 유통.
- **base value = 계층형 floor (2요소, 상장 시 1회 산정)**:
  - **① 포지션 baseline**(1차 요소) — 포지션별 기본가 테이블(Enum/Map, O(1)).
  - **② 팀 tier 배수** — 2023 순위 기반 2~3단계.
  - **③ 2023 개인 스탯(rating+골+어시)이 있으면 상향 반영**, 없으면 `포지션baseline × 팀tier`.
  - **스탯 없는 선수**(2부 승격·이적·신인/유망주·api 공백)는 `포지션baseline × 팀tier`로만 산정. 대형 영입과 무명이 같은 초기가여도 **MVP는 수용** — base value는 "출발점"이고 **P2P 시장이 재가격**한다. 개별 override 없음(YAGNI).
  - **승격 팀**(2023 K리그1 순위 없음)은 **최하 tier** 기본값.
  - 전부 **튜닝 상수**. 근거: 시즌 개인스탯 sparse → 단일 flat floor는 **분배 왜곡**(시스템 시드 front-run). 계층형은 **분배 공정성**을 위함(P2P라 인플레 위험은 아님).
  - 이후 성적은 가격 직접 안 건드림(배당만).
- **초기 매수 상한**: **상시 per-user per-player 보유 상한(constant cap)** — `보유+주문 ≤ cap` O(1) 체크. front-run + 한 선수 매점 집중 동시 억제. 튜닝 상수. (시간 쿨타임은 선택적 추가)
- **2024 시즌 데이터로 라이브 테스트**(경기·배당 진행).

### D2. 포인트 경제
- 가입 시 **시작 포인트 지급(넉넉히)**, 구체 금액 미정.
- 소스: 배당(시스템 발행) + 시작 포인트 / 싱크: 시드 물량 매수 → **약인플레 게임경제로 의식적 허용**.
- **MVP엔 파산 방지 장치 없음(YAGNI).** "항상 되팔기" 보장은 2차 마켓메이커(bid 공급)로. 친구초대 포인트 2차.

### D3. 배당 규칙
- **기준시점(스냅샷)**: **경기 킥오프 시점의 보유자**에게 지급(정산 직전 매수→먹튀 방지). 거래는 계속 열림.
  - **체결 완료(filled) 기준** — 미체결 매수 주문(에스크로 예약)은 보유 아님, 제외.
  - **경계 판정**: 벽시계 ms가 아니라 **불변 이벤트 로그 순서(sequence)**로 — "킥오프 직전 마지막 이벤트까지의 보유"(strictly-before). 동시각 tie는 sequence로 결정론적 해소.
  - **연기 경기**: **실제 킥오프 시각**으로 스냅샷(예정 시각 아님). **취소 경기**: 스냅샷 폐기·정산 없음.
- **공식 = 범용 2성분 가산 모델** (포지션 분기 없음 — 전 선수 동일 로직으로 자연스러운 차등):
  - **팀 성분**: 승/무실점(클린시트)/실점 등 팀 결과 → **그 경기 출전자에게 1/n 분배**.
  - **개인 성분**: 골·어시·페널티(+자책골·레드 상쇄) → 기록한 선수에게.
  - **총 배당 floor at 0** (클로백 없음). 부정 스탯은 개인 성분에서 상쇄만.
  - 결과: 공격수는 개인 성분↑, 수비수는 팀 성분↑ — **포지션 분기 하드코딩 없이 수식에서 자연히 갈림.**
  - rating 기반 폐기 이유: per-match rating이 ~35% 경기만 있어 **불안정**(데이터 현실 참조) → 전 경기 가용한 events+팀결과로.
  - 가중치는 **튜닝 상수**.
- **출전자 정의**(1/n 대상): **`fixtures/lineups` 선발(startXI) ∪ `fixtures/events` 교체 IN.** (벤치만 앉은 선수 제외. per-match `minutes`는 ~35% 경기만 와 **불안정**하므로 그걸로 정의하지 않음.)
- **배당 정책 세부(엣지 케이스)**:
  - **교체 선수**: **출전자 전원 균등 1/n**(선발·교체 동일). minutes는 ~35% 경기만 와서 부분 사용 시 경기 간 불공정(rating과 동일 이유) → 미사용. **완전한** minutes 소스가 생기면 시간 비례로 확장할 수 있게 **추상화 여지**만 둠.
  - **레드(퇴장) 선수**: **팀 성분에서 제외** → 개인 성분만(floor 0). 승리 보상을 안 받아 방어 가능, **음수 배당(클로백) 없이** 처리.
  - **자책골**: 팀 성분 하락(실점→클린시트 상실)은 **출전자 전원 공유**, 개인 페널티는 자책 선수만 → **축이 달라 이중처벌 아님**(의도). floor 0로 음수 방지.
  - **다중 이벤트**(골+레드 등): 개인 성분 = 해당 선수 이벤트 기여 **합산**(골+어시+페널티 − 자책 − 레드) 후 총배당 floor 0.
  - **중복 이벤트 dedup**: **옐로2 = 퇴장 1회**로 처리(옐로+옐로+레드 중복 집계 금지).
  - **PK 골**: **일반 골과 동일**(MVP). "데이터가 Penalty를 구분함 ≠ 다르게 평가할 근거" — 정당화 없는 차등 안 둠(프로젝트 철학과 일치). **튜닝 가능 정책**으로 두고 운영 데이터가 왜곡 보이면 조정. (승부차기 골은 K리그1 정규리그엔 없음 → N/A)
  - **VAR / 최종 이벤트**: 골 취소 등은 **최종 공식 이벤트 기준**(grace period로 대부분 흡수).
  - **선수 이적**: 주식은 **선수 귀속**(팀 아님) — 이적해도 보유 유지. 배당은 **각 경기에서 실제 뛴 팀** 기준(경기 데이터). K리그1 밖으로 이적 시 배당 중단(시장이 재가격).
  - **미출장(DNP)**: 명단 포함이라도 미출전이면 출전자 아님 → **배당 없음**.
  - **Grace period 표시**: 확정 전엔 **예상 배당(잠정) 표시 가능**하되 **잔고 반영(원장 기입)은 finality에서만**.
  - **경기 상태**: **정상 종료(FT) + 데이터 완비 경기만 정산**. 취소·연기·중단 스킵(재개는 최종 FT 시 정산). 몰수는 공식 결과 있으면 반영, 없으면 스킵.
  - **데이터 정정 재정산**: **FT 후 유예시간(grace period) 경과 뒤 1회 확정**, 이후 API 정정에도 **재정산 안 함**(finality 우선 — 재정산은 이미 쓴 포인트 클로백 혼란). 유예로 초기 오류 완화.
  - **floor 0의 비용(알려진 한계)**: 0 근처 페널티 그라데이션 소실(골+5/레드−10 = 레드−10 = 0). 음수 floor·시즌 누적 페널티는 **미룸**.
- **공정성 한계(데이터 부재)**: 이벤트 공격수 편중 → 공격수 배당·수요 쏠림 우려. 완화: ① 팀 성분 가중치 상향(튜닝) ② 클린시트 보너스로 수비/GK 보상 ③ 시장 자기보정(공격수 가격↑→배당 수익률(yield)↓). **근본 해결 = 수비 지표 확보(지속 연구 과제).**
- **정수/소수 정책**: 포인트는 **정수 minor-unit 스케일**(예: 내부 ×100 정수)로 저장·연산, **float/double 금지**. 스케일로 작은 배당이 0으로 소멸 방지.
  - **1/n 나머지 = 시스템이 미발행**(배당은 시스템이 발행하므로 나머지는 애초에 유저 것이 아님 — "빼앗음"이 아니라 "덜 발행", 총량 보존 + 미세 인플레 싱크). 나머지는 배당당 최대 (n−1) minor-unit(<0.2pt)로 무시 가능. 대안(최대지분자=편향 / 랜덤=비결정성 / 이월=과복잡·상장폐지 잔량 엣지)은 기각.
- **멱등**: **(경기, 선수) 단위 1회.** **앱 레벨 체크(정산 기록 존재 여부)로 스킵 + DB 유니크 제약 `(fixture_id, player_id)`로 최종 방어** — 앱 체크만으론 동시 실행 race condition 가능하므로 DB가 진실의 방어선.
- **타이밍**: 경기 종료 감지 시 배치 정산. 배당 규모(base value 대비)도 튜닝 상수.

### D4. 주문 의미론 (구체 엔드포인트·스키마 = `docs/api/openapi.yaml`)
- **동기/비동기**: 주문 제출은 **동기**(즉시 매칭 시도 후 결과 반환), 응답은 "체결됨"이 아니라 **"주문 접수됨 + 즉시 체결분"**. 지정가는 반대편 호가가 없으면 호가창에 남으므로. 잔량의 이후 체결은 비동기적 성격 → 조회로 확인.
- 지정가만(MVP) · **정수 주 단위** · `limitPrice` = 한도가(매수 최대지불/매도 최소수취).
- **부분 체결** 허용 · **가격-시간 우선순위** 매칭.
- 생명주기: `OPEN → PARTIALLY_FILLED → FILLED / CANCELLED`. 취소 = 잔량 취소.
- **유효기간·수정**: MVP는 **GTC**(취소 전 유효, 만료 없음). 만료(TTL·DAY 주문)는 2차. **주문 수정(amend) 미지원 → 취소 후 재주문**(취소=예약 전액 반환, 재주문=재예약; in-place 수정을 나중에 넣으면 예약 원자적 조정 필요). **상장폐지(D9) 시 해당 선수 잔여 주문은 자동 취소·예약 반환.**
- **에스크로**: 매수=`한도가×수량` 포인트 예약, 매도=`수량` 주식 예약. 미체결 잔량은 예약 유지→취소 시 반환, 체결 시 이전.
- **매칭 실행·동시성**(→ ADR-0005): MVP는 **요청 스레드 동기 매칭(선수별 직렬화)**. 큐 기반 비동기 엔진은 나중.
  - **락 점유 최소화**: 임계 구역 안에서는 **호가창 조회 → 매칭 → 체결·정산 저장**만. **외부 API 호출·긴 연산은 락 밖으로**(외부 데이터는 배당 배치·로스터 동기화 등 별도 흐름; 매칭 트랜잭션은 순수 DB). 성능·데드락 방지.
- **주문 처리 세부**:
  - **원자성**: 주문 생성 → 매칭 → 체결(fill) 생성 → 잔고·보유 정산 → 잔량 호가 등록 = **단일 트랜잭션**. 중간 실패 시 **전부 롤백**(부분 체결도 미저장).
  - **fills 순서**: **가격-시간 우선순위**(최우선가부터, 동일가는 FIFO). 예: 매도 3/4/2주에 7주 매수 → 오래된 3·4주 순서로 체결(2주 미체결).
  - **체결가 = maker의 `limitPrice`**. 신규 주문(taker)이 반대편 호가창의 기존 주문(maker)과 교차하면, **각 fill의 가격은 그 maker의 한도가**다. taker의 한도가는 **교차 여부만** 판정하고(매수 taker면 `maker가 ≤ taker가`, 매도 taker면 `maker가 ≥ taker가`) 체결가에는 관여하지 않는다. 매수 한도 102가 매도 한도 100과 만나면 **100**에 체결 — 차액(가격 개선분)은 **taker**가 가져간다. taker 잔량이 호가창에 등록되면 **그때부터 그 주문이 maker**이고, 이후 체결가는 그 주문의 한도가다.
    - **불변식**: 체결가는 언제나 maker 한도가 · 매칭 후 `best bid < best ask`(크로스드 오더북 없음) · 매수 실지불 ≤ 예약액이고 매도 수취 ≥ 자기 한도가(양쪽 다 한도 위반 없음).
    - **왜 maker인가**: 지정가 호가창의 표준이고, 이래야 체결가가 호가창의 실제 공급가에 묶여 D0의 가격 발견과 D8의 조작 내성이 성립한다(taker 가격이면 한도가를 높게 걸어 최근 체결가를 혼자 끌어올릴 수 있다).
    - **"먼저"의 정의**는 벽시계가 아니라 **선수별 직렬화 지점 도달 순서**(아래 *동시 주문* 항목).
    - **여러 가격대와 교차하면 fill마다 체결가가 다르다.** 매수 7주@102 vs 호가창 `[매도 100×3, 101×4]` → `fills=[{100,3},{101,4}]`. `fills[].price`가 원소별로 있고 `avgFillPrice`가 자명하지 않은 이유다.
    - **avgFillPrice 반올림**: `Σ(체결가×수량) ÷ Σ수량`을 **HALF_UP**(0.5는 올림)으로 정수 반올림(`704/7 = 100.57… → 101`). **매수·매도 동일 적용** — 방향을 나누는 건 평균가가 정산에 쓰일 때 반올림으로 돈이 생기지 않게 하려는 조치인데, 여기선 표시용이라 그 동기가 없다. 편향이 누적될 곳이 없으므로 HALF_EVEN이 아니어도 된다.
      - **평균의 평균을 내지 않는다** — 수량이 다르면 틀린다(`[100×6, 101×1]` → 평균의 평균 101, 올바른 값 `701/7 = 100.14 → 100`). 언제나 원본 fills에서 재계산한다.
      - 체결 0건이면 **null**. 미체결·취소 수량은 분모에 넣지 않는다(부분체결 후 취소면 체결된 수량만).
      - **표시용이며 정산 기준이 아니다.** 정산의 원본은 fills다. 반올림이 손실적이라 `avgFillPrice × filledQuantity ≠ 실제 체결금액`(101×7 = 707 ≠ 704) — 금액이 필요하면 fills를 합산한다. `totalFillAmount` 필드는 fills로 복원 가능해 두지 않는다(fills에 절삭이 생기면 그때 추가).
    - **첫 거래**: 호가창에 시스템 시드 매도호가만 있으므로 시스템이 maker → 첫 체결가 = base value(시드는 D0, base value 정의는 D1).
    - **자기 자신과 교차**는 체결가 규칙보다 **STP가 먼저** 걸린다(D7 Cancel Taker) — 체결 자체가 없다.
  - **에스크로 차액**: 매수 예약은 `한도가×수량`인데 maker 가격 체결이면 실제 지불이 더 적다. **다만 반환 이벤트는 없다** — 예약액은 저장하지 않고 미체결 주문에서 유도하므로(아래) 예약 자체가 차감이 아니다. 잔고에서 빠지는 것은 **실제 체결금액뿐**이고, 유도되는 예약액은 잔량이 줄면서 자동으로 갱신된다. 원장에 남는 것은 체결 하나뿐이라 append-only(ADR-0006)와 충돌하지 않고, `LedgerType`에 에스크로용 타입이 필요 없다. **차액은 그 주문이 taker로 체결된 수량에서만 생긴다**(주문 단위가 아니라 fill 단위 — 한 주문도 즉시 체결분은 taker, 호가창에 남은 잔량은 maker로 역할이 갈린다). 잔량이 나중에 체결될 땐 자기가 maker라 체결가 = 자기 한도가 = 예약가이므로 차액이 0. 따라서 미체결 예약액은 항상 `Σ(잔량 × 한도가)`로 유도된다. **이 성질은 체결가 = maker 한도가라는 위 규칙에 의존한다** — taker 가격 정책이면 기다리던 매수 102가 새 매도 100과 100에 체결되어 maker 쪽에도 차액이 생긴다.
    - 가격 차액과 **미체결 수량의 예약 해제는 별개**다. 후자의 경로는 **MVP에선 둘 — 취소 · STP Cancel Taker(D7)**. 상장폐지 자동 취소(D9)는 폐지 **실행이 2차**라 그때 셋째 경로가 된다. 만료는 GTC라 없다(위 *유효기간* 항목).
  - **주문 레코드**: orderId는 **생성(매칭 전) 시점 발급**. 즉시 100% 체결돼도 **order 레코드 영속**(status=FILLED) — 감사·내역·fill 참조.
  - **평균 체결가**: 응답에 **avgFillPrice 포함**(서버가 Σ가격×수량/Σ수량 계산). 클라 중복 계산·불일치 방지, 파생 비용 ≈0.
  - **동시 주문**: 같은 선수 주문은 **선수별 직렬화**로 순서화 → 직렬화 지점 도달 순서 = 시간 우선순위. 진짜 "동시"는 없음.
  - **취소 vs 체결 동시**: 직렬화라 **락 획득 순서가 승자**. 취소 먼저 → 체결 없음 / 체결 먼저 → 취소는 잔량만(전량 체결이면 `ORDER_NOT_CANCELLABLE`). **절대 둘 다 성공 안 함**(이중 지불 없음).
  - **부분체결 직후 취소**: 취소는 **잔량만**. 예: 10주 중 6주 체결 후 취소 → 6주 FILLED(정산 완료), 4주 CANCELLED(예약 반환), 주문 상태 CANCELLED(filledQty=6).
  - **이후 체결 알림**: MVP는 **폴링**(주문 상태·원장 조회). 2차는 **SSE / WebSocket / Push** 중 택.
- 구체 엔드포인트/요청·응답 스키마는 **`docs/api/openapi.yaml`** 참조(작성 완료).

### D5. 인증 (MVP 포함, 단 개발 순서상 1순위는 아님 — 트레이딩부터) (→ ADR-0003)
- **클라이언트**: 웹 + **모바일**(비전상 필수). → 인증은 **헤더 Bearer 토큰**(쿠키 아님).
- **토큰 상태**: MVP는 **서버측(opaque) 토큰** — 무효화 쉬움·단순·모바일 호환. **무상태 JWT는 멀티서비스/수평확장 필요 시 전환**(ADR + 메커니즘 격리).
  - 근거: 모바일은 "쿠키 vs 헤더" 축만 뒤집음(→헤더). "서버측 vs 무상태" 축은 규모가 결정 → 아직 서버측. JWT의 무상태 이점은 지금 불필요하고 리프레시 회전·블랙리스트 비용만 발생.
  - 구현 후보: Spring Session 헤더 세션 리졸버 또는 단순 토큰 스토어.
- **비밀번호 BCrypt 해시**(평문 금지). 가입/로그인/로그아웃/내 정보.
- **토큰 생명주기**: **만료 있음**(응답 `expiresIn` 초로 노출) + 로그아웃 시 즉시 무효화. 구체 만료 시간은 튜닝 상수. 리프레시 토큰은 미룸.
- **메커니즘 격리**: 컨트롤러·서비스는 세션/토큰을 모르고 `CurrentUser`/`SecurityContext`에만 의존 → 전환 비용 최소.
- **보호 범위**: 주문·포트폴리오·거래내역 = 인증 필요. **시세/마켓 조회 = 비로그인 공개.**
- **다계정 공격(sybil)**: 포인트가 보상으로 이어지므로 "이득 없음"이 아니다. 완전 방어(전원 신원 인증)는 과투자 → **방어를 "보상 경계"에 집중**: ① 랭킹 지표 조작 내성(D8) ② **보상 자격만** 신원 검증(전체 유저 아님) ③ 상위 수상자 **수동 감사**. 실시간 전 거래 sybil 방어는 하지 않음. 기본기(계정당 보유 상한·자전거래 방지(STP)·레이트리밋)는 유지.
- 미룸: 소셜/OAuth, 이메일 인증, 비밀번호 재설정, 리프레시 토큰, 역할·권한 체계.

### D6. 선수 유니버스 / 데이터 (→ ADR-0004)
- **거래 유니버스 = 2024 K League 1(league 292) 전체 로스터**(시뮬레이션 시즌 선수). "1부만" 자동 충족.
- 로스터 소스: `players?league=292&season=2024`(~35p) 또는 `players/squads`(팀별). 메타(포지션·팀·사진) 포함.
- base value용 2023 스탯: `players/topscorers`·`topassists` + `players`(있는 것만); 없으면 D1 계층형 floor.
- 경기결과·성적 수집(배당용): `fixtures`(종료 감지) + `events` + `lineups` → 2024 시즌 배치.
- **데이터 소스 = api-sports 단일**(합법 사용). K리그 공식 포털은 **ToS상 저장·활용 금지**(보도 목적 외 사전허가 필요)라 **배제**.
- **어댑터(Anti-Corruption Layer)**: `kleague-client` 모듈이 api-sports DTO → 도메인 모델(`SeasonStats`/`MatchPerformance` 포트) 변환 전담. 도메인·배당엔진·DB는 api-sports를 **모름** → 제공자 교체 시 이 모듈만 수정. (= 모듈 ADR "kleague-client 분리 근거"의 구체화)
- **식별자 격리**: 선수·경기는 **내부 id(PK) 발급**, api-sports id는 매핑 컬럼(`api_sports_id`)으로만 보관·**미노출**. 제공자 교체 시 공개 API id 불변(ACL의 완성).

### D7. 수수료 / 스팸 방어 / 자전거래
- **거래 수수료**: **소액 명목 수수료(예 0.2%, 튜닝 상수)** — 체결(fill) 시 부과 → **포인트 싱크**로 배당 인플레 완화. 부분체결 반올림/버림은 D3 정수 minor-unit 정책 따름.
- **스팸/DoS 방어 = 레이트리밋(별개 문제, 상시 필수)**: 체결 수수료는 **미체결 주문 스팸을 못 막음**(체결 안 되면 수수료 0) → **유저당 주문 생성/취소 rate limit** 필수. 수수료 유무와 무관.
- **자전거래 = STP(Self-Trade Prevention)** — **매칭 엔진 정책**(지정가·시장가 등 주문 타입 무관, 시장가 도입 시에도 동일 적용):
  - 단순 "매칭 스킵"은 **크로스드 오더북**(bid≥ask 잔존) → 금지.
  - **Cancel Taker**: taker가 **자기 호가와 체결될 첫 순간 taker 잔량 전부 취소·예약 반환**(타 유저 호가엔 가격-시간 우선순위대로 먼저 체결).
  - **예시**: 매도 `[B 3주@100(오래됨), A 10주@100]`. A가 매수 8주@100 → B 3주 체결(A 잔량 5) → 다음이 A 자기 매도 → self-trade 감지 → **A 잔량 5 취소**. A 자기 매도 10주는 그대로.
  - 수정=취소+새 주문이라 STP는 **새 주문 기준 자동 재검사**.
  - **취소(STP 자동 취소 포함)도 이벤트 로그에 기록**(D8 재구성·감사·멱등). 종료된 주문 취소는 no-op(ORDER_NOT_CANCELLABLE).

### D8. 랭킹 / 포트폴리오 가치
- **포트폴리오 가치 = MVP 포함**: `현금 + Σ(보유수량 × 최근체결가; 미거래 선수는 base value 폴백)`. "지시적 평가값, 실현가 보장 아님" 명시. 여기서 **현금·보유수량은 예약분을 포함한 총액**이다(D4 에스크로) — 예약 현금은 아직 안 쓴 돈, 예약 주식은 아직 내 주식이라 이중계산이 아니다.
- **랭킹(리더보드) = 2차**: 핵심 루프 아님(YAGNI). 단, 포인트가 **보상**(유니폼·다음 시즌 포인트 등)으로 이어지므로 랭킹 지표는 **조작 내성**이 있어야 함:
  - **최근 체결가 기반 포폴가치로 랭킹 금지** — 다계정 자전거래(자기 계정끼리 거래)로 최근가를 조작 가능.
  - 랭킹 = **실현 손익(realized, 실제로 남에게 판 손익)** + **보수적 평가**(거래량 가중 평균가(VWAP) 또는 최우선 매수호가(best-bid))로 계산 → 자기 계정끼리 자전거래해도 순위가 안 오름(순 실현가치 0−수수료).
  - MVP 포폴 **표시**는 최근가 OK, **랭킹 계산**만 조작 내성 지표 사용.
- **랭킹 정책 확정 = MVP2**, 방향 = **총자산 기반(A)**(모두 같은 시작금이라 총자산=총수익 순위 동일). MVP는 랭킹 계산을 **하지 않고**, 어떤 알고리즘에도 대응하도록 **원천 데이터 완전·불변 적재**에 집중:
  - 미실현 보유분 평가는 **"랭킹 가격(Ranking Price, 조작 내성 평가가)" 추상 정책**(도메인 포트, 교체 가능)으로 — 최근가 아님, 공식은 **실거래 백테스팅(backtesting)**으로 결정.
  - 적재: **불변 원장(append-only ledger) + 주문 이벤트 로그** → 과거 시점 호가창 **재구성 가능**(이벤트 소싱(event sourcing)). 잔액·평균 매입가(avgCost)는 이 로그에서 재계산되는 **파생값(projection)**. 주기적 호가창 스냅샷은 성능 체크포인트로 **선택**.
  - 이 데이터 캡처 아키텍처 = **ADR-0006**. ⚠️ 이건 캡처일 뿐 — 이벤트소싱 **비동기 매칭 엔진**(ADR-0005의 번복 대안)과는 별개(스코프 크립 금지).

### D9. 선수 라이프사이클 / 상장폐지(delisting) (→ ADR-0007)
- **문제**: 선수가 K리그1을 떠나면(이적·은퇴·군입대·K2 이적) 경기·배당이 끊긴다. 전원이 팔려 하지만 매수가 없어 **가격 폭락이 아니라 유동성 소멸**(거래 자체가 안 됨) → 거래 불가 자산이 누적.
- **결정**: **상장폐지를 도메인 라이프사이클 이벤트로** 모델링(Inactive 누적보다 깔끔, "선수 = 상장 자산" 컨셉과 부합).
  - 상태: **ACTIVE → DELISTING_PENDING → DELISTED**
  - `DELISTING_PENDING`: 이탈 확정 후 **거래 N일 유지**(exit 창; 즉시 폐지는 악용 가능) → 이후 **거래 정지**
  - `DELISTED`: **최종 정산금 지급 → 보유 주식 소각**(공급 0, 유니버스에서 제거)
- **정산가**: 최근 체결가 아님 → **조작 내성 참조가**(D8 Ranking Price와 **동일 추상 재사용**, 예: 정지 전 window의 거래량 가중 평균가(VWAP)). 시스템이 정산금 발행, 주식 소각.
- **트리거 감지(어려운 부분)**: K리그1 이탈 판정 — `/transfers` 또는 "KL1 스쿼드에서 사라짐" 휴리스틱. lag·모호성 가능 → grace window가 흡수, **수동 override** 허용.
- **하드 삭제 금지**: `DELISTED`는 **soft 상태** — 선수 레코드는 원장·체결·보유가 참조하므로 **DB에 남긴다**(참조 무결성). 유니버스·거래에서만 제외.
- **상태 → 노출값 매핑**: `tradable`은 저장 필드가 아니라 **라이프사이클 상태 × 구간에서 파생**된다. `DELISTING_PENDING`이 exit 창(거래 O)과 창 종료(거래 X) 두 구간을 담으므로 상태:사유가 1:1이 아니다 — 그 모호성을 이 표로 해소한다:

  | 라이프사이클 상태 | 구간 | `tradable` | `tradableReason` |
  |---|---|:---:|---|
  | `ACTIVE` | — | `true` | `null` |
  | `DELISTING_PENDING` | exit 창 열림 | `true` | `null` |
  | `DELISTING_PENDING` | 창 종료(정지) | `false` | `HALTED_DELISTING` |
  | `DELISTED` | — | `false` | `DELISTED` |
  | (임의 상태) | 운영 정지 | `false` | `SUSPENDED` |

  - `HALTED_DELISTING` = "`DELISTING_PENDING`이면서 exit 창 종료" 구간으로 **정의**된다.
  - `SUSPENDED`는 라이프사이클과 무관한 **운영상 거래 정지**(데이터 이상·점검 등). 어느 상태에서든 발생 가능.
  - **주문 거부**: `tradable=false`면 사유와 무관하게(`HALTED_DELISTING`·`DELISTED`·`SUSPENDED` 모두) **409 `MARKET_CLOSED`**. `DELISTED`도 레코드가 남으므로 404가 아니다. 사유 구분은 `GET /players/{id}`의 `tradableReason`으로 한다.
  - ⚠️ **2차 구현 시 필수**: exit 창 중에는 `tradable=true`·`tradableReason=null`이라 유저가 "곧 폐지된다"는 걸 알 방법이 없다 → 창이 무의미해진다. 상장폐지 구현 시 **`lifecycleState`를 마켓 응답에 노출**한다. (MVP엔 폐지 기능이 없어 지금 필드 추가는 안 함 — YAGNI)
- **스코프**: 라이프사이클 상태·정산 **정책은 설계 확정**, 자동 감지+정산 **실행은 2차(또는 수동)**. MVP는 2024 시즌 활성 선수로 상장, 이탈 자동 처리는 미룸(transfer-detection 스코프 크립 방지).

## MVP 기능 목록

- **인증**(D5): 회원가입·로그인·로그아웃·내 정보. 헤더 Bearer(서버측 토큰), BCrypt 해시, `CurrentUser` 추상. 보호: 주문·포폴·내역 / 공개: 시세·마켓.
- **선수·마켓**(D1·D6): 2024 K리그1 전체 로스터 상장(선수당 고정 N주). base value = 계층형 floor(포지션 × 팀tier, 2023 스탯 있으면 상향). 시스템 전량 시드. 마켓 목록·시세·**호가창 조회**(공개, 가격별 잔량 집계 — 지정가 전용이라 가격별 잔량이 안 보이면 몇 주를 살 수 있는지 모른 채 주문하게 된다).
- **거래/매칭**(D0·D4·D7): 지정가 주문 생성(동기, 접수+즉시체결분)·취소, 부분체결, 가격-시간 우선순위, 에스크로 예약/원자적 정산, 선수별 직렬화, STP(Cancel Taker), 소액 수수료, 유저당 주문 rate limit, 상시 per-user per-player 보유 상한.
- **포트폴리오/내역**: 보유 조회, 포폴가치(D8), **통합 원장**(체결·배당·입금, `/me/ledger`).
- **배당 파이프라인**(D3): 2024 경기 종료 감지 배치 → events+팀결과 **2성분 가산 배당**. 킥오프 스냅샷 보유자, 출전자=라인업+교체, floor 0, (경기,선수) 멱등, 정수 minor-unit.
- **데이터 수집**(D6): `kleague-client` 어댑터가 api-sports → 도메인 모델(로스터·경기·events·lineups).
- **경제**(D2): 가입 시작 포인트, 파산방지 없음.

**구현 순서 힌트**: 트레이딩 도메인부터(인증은 1순위 아님). 계약 우선 — API 스펙 → API 스펙 기반 통합테스트(컨트롤러+DTO 더미, 서비스 없이) → 유닛 → DB → 실로직.
