`docs/`의 설계 문서들이 서로 어긋나지 않는지 검사한다. **읽기만 한다. 절대 고치지 않는다.**

문서가 많아지면 같은 사실을 여러 곳에 적게 되고, 한쪽만 고치면 조용히 어긋난다. 그 어긋남을 구현 착수 전에 찾는 것이 목적이다.

## 검사 대상

| 파일 | 무엇 |
|---|---|
| `docs/superpowers/specs/2026-07-29-kleague-market-design.md` | 설계 스펙. D0~D9 결정 · MVP 기능목록 · 미룸 목록 |
| `docs/adr/0001~0008-*.md` | 아키텍처 결정 기록 |
| `docs/adr/README.md` | ADR 목록 표 |
| `docs/api/openapi.yaml` | 기계용 API 계약 |
| `docs/api/README.md` | 사람용 API 요약 + 공통 규약 |
| `docs/README.md` | 위키 규칙 · 기억 시스템 경계 |
| `docs/workflow.md` | 작업 방식 · 세션 규칙 |

먼저 `Glob`으로 `docs/**/*.md`와 `docs/**/*.yaml`을 훑어 위 목록에 없는 새 문서가 생겼는지 확인하고, 있으면 그것도 대상에 넣는다.

## 검사 축

### 1. 교차 모순
같은 사실을 두 문서가 **다르게** 말하는 것. 가장 심각하다.

수수료율, 배당 스냅샷 기준, 상태 이름(`ACTIVE`/`DELISTING_PENDING`/`DELISTED`), 필드 타입, 엔드포인트 경로·인증 요구, STP 정책, 출전자 정의 등 — 두 곳 이상에 나타나는 값은 전부 대조한다.

### 2. ADR ↔ 스펙 참조 무결성
- 스펙 안의 `(→ ADR-000N)` 표기가 실존하는 ADR을 가리키나
- 그 ADR의 결정 내용이 스펙 서술과 실제로 일치하나 (링크만 맞고 내용이 다른 경우가 흔하다)
- `docs/adr/README.md`의 목록 표가 실제 파일 목록·제목·상태와 일치하나
- 스펙 헤더의 ADR 나열(`0001 멀티모듈 · 0002 거래모델 · …`)이 현재 ADR 개수와 맞나

### 3. API 계약 ↔ 스펙
`openapi.yaml`이 `api/README.md`의 공통 규약과 설계 스펙을 반영하는지:
- money 필드가 `type: integer, format: int64`인가 (`number`/`float` 금지)
- quantity가 `int`인가
- 시각 필드가 `format: date-time` + UTC 서술인가
- 페이징 응답에 `page`/`size`/`totalElements`/`totalPages`가 있나
- `tradableReason`, `avgFillPrice` 등 나중에 추가된 필드가 세 문서(스펙·README·yaml)에 다 반영됐나
- `api/README.md`의 엔드포인트 표와 `openapi.yaml`의 path 목록이 일치하나 (한쪽에만 있는 엔드포인트)

### 4. 위키 링크
`[[노트명]]` 형식 링크가 실존 파일을 가리키는지 확인한다.

⚠️ **중요한 예외**: `docs/README.md`는 "새 개념은 본문에 `[[새 노트]]`로 먼저 연결해 두고, 필요할 때 실제 파일 생성"을 **의도된 정책으로 허용**한다. 따라서 파일이 없는 위키 링크는 **결함이 아니라 `미작성` 항목**이다. `모순`이나 `불일치`로 올리지 말고 `미작성` 심각도로 목록만 제시한다.

### 5. stale 용어
이미 폐기된 결정의 잔재가 남아 있는지. 폐기된 것들:
- **rating 기반 배당** — per-match rating이 ~35% 경기만 있어 폐기, events+팀결과 2성분 가산으로 대체
- **minutes 비례 배당** — 같은 이유로 폐기, 출전자 균등 1/n
- **AMM / 시스템-상대 거래** — P2P 호가창으로 대체
- **최근 체결가 기반 랭킹** — 자전거래 조작 가능해 폐기, Ranking Price 추상으로
- **"별도 작성 예정" 류의 완료된 TODO**

### 6. 미룸 ↔ MVP 경계
설계 스펙의 "미룸 (2차+)" 목록에 있는 항목이 "MVP 기능 목록"에도 들어가 있지 않은지. 반대로 MVP 기능인데 어디에도 API 계약이 없는 것도 본다.

## 출력

심각도별로 묶어서 보고한다. 항목마다 **`파일:줄`**, **양쪽 원문 인용**, **왜 문제인지 한 줄**.

```
## 모순 (두 문서가 다르게 말함)
1. 거래 수수료율
   - specs/2026-07-29-kleague-market-design.md:XX — "소액 명목 수수료(예 0.2%)"
   - api/README.md:XX — "0.5%"
   → 구현 시 어느 쪽을 따를지 알 수 없다

## 불일치 (한쪽에만 있거나 반영 누락)
...

## 미작성 (의도된 미래 노트 — 결함 아님)
...

## 참고
...
```

각 항목에 **고칠 방향**을 한 줄 덧붙인다. 어느 쪽이 최신인지 판단 근거(커밋 순서, 더 구체적인 서술 등)가 있으면 함께 적는다.

문제를 못 찾았으면 "축 N: 이상 없음"으로 축별 결과를 명시한다. 무엇을 확인했는지 드러나야 신뢰할 수 있다.

## 하지 않는 것

- **파일 수정 금지.** 보고만 한다. 고치는 판단은 메인 세션에서 한다 — 명백한 위반은 즉시 반영, 판단이 갈리는 건 사람에게 넘긴다.
- 문체·오타 지적 금지. 정합성만 본다.
- 설계 자체에 대한 의견 금지. "이 결정이 별로다"가 아니라 "이 결정이 저기와 어긋난다"만.
